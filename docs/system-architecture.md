# Friday System Architecture

Last updated: 2026-10-24 (plans 1-7 done: the engine runs on Discord with memory, effect tools, files in both directions and no leftover engine code). Target design: [2026-10-23-friday-team-engine-design.md](superpowers/specs/2026-10-23-friday-team-engine-design.md).

## Now
- `bun run start` (`apps/friday/src/index.ts`) checks the config and the credential (`CLAUDE_CODE_OAUTH_TOKEN`), refuses an `AGENT_HOME` inside a git working tree, creates the home, starts the trash and home-retention sweepers, then runs the engine (`startEngine` in `apps/friday/src/main.ts`): it refuses by name (`DISCORD_TOKEN missing`, `DISCORD_GUILD_ID missing`, `OWNER_DISCORD_ID missing`) before any network call, connects to Discord, builds `ClaudeRuntime` and `startApp`, logs `engine.started` and runs until SIGINT / SIGTERM (then `app.stop()`, the Discord client closes, the sweepers stop). Env keys: `CLAUDE_CODE_OAUTH_TOKEN`, `AGENT_HOME`, `LOG_LEVEL`, `DISCORD_TOKEN`, `OWNER_DISCORD_ID`, `DISCORD_GUILD_ID` (`src/config/agent-config.ts`).
- `src/` holds only the process entry: `index.ts`, `lifecycle/` (boot, boot checks, home placement check, trash and home-retention sweepers), `config/` (env, home paths, model ids), `observability/` (pino logger and log files).
- Removed: chief-of-staff / worker / goal / plan engine, the old Discord surface, the old SQLite db and its migrations, presets and roles as files, the old MCP servers, artifacts store and viewer, ops dashboard, dreaming and episodes. Data of older builds in `AGENT_HOME` is ignored, never opened or deleted.

## `packages/core` (plan 2)
Domain, ports and use cases; no dependencies, imports only itself (`packages/core/test/core-boundary.test.ts`). Ports are in [`packages/core/src/ports/`](../packages/core/src/ports/): `AgentRuntime` (+ `BotSession`, generic `RuntimeEvent`), `Surface`, `Store`, `ToolCatalog`, `Memory`, `Clock`.
- **Routing** (`routing/`): `@name` parsing; direct chat goes to its bot, a group message to the mentioned members or the entry bot, a bot reply wakes no one: bots reach each other only through the `SendToBot` and `HandOff` tools (`BotMessenger`). `ChainGuard` caps hops, bot messages per hour and bot repeats.
- **Permission** (`permission/`): `decide` is pure: hard-floor deny, tool override, matching grant, then the autonomy level (careful / balanced / autonomous) for the tool's class from its annotations. Unannotated = ask; irreversible = ask always (no "Always allow"). `PermissionGate` asks through the `Surface`, stores grants, audits, and denies on timeout.
- **Hub** (`hub/`): `BotHub` keeps one session per bot and scope (direct, or one per group the bot works in), pushes one turn at a time (a message to a busy bot waits for the turn to end), stores every bot-to-bot wake in the `wakes` table (lifecycle `queued/running/done/blocked/interrupted/dropped`, redelivered once after a restart by `recover()`), keeps the shared ticket board (`TicketBoard`: assigning a ticket wakes the assignee; a ticket left open after a turn gets one re-wake, then is blocked), returns a finished request to its sender as a `result`, applies the daily spend cap, closes idle sessions, resumes after a crash, and serves `stop` and `status`.
- Defaults: `packages/core/src/config-defaults.ts`.

## `packages/store-sqlite` and `packages/config` (plan 4)
Bots and groups are files; the db holds the rest. `apps/friday` joins them: `{ ...engineStore, bots, groups: config.groups }` is the core `Store` (the Friday bot gets its real dirs filled in).
- **Engine db** (`store-sqlite`): `openEngineDb(file)` (WAL, owner-only file and sidecars, refuses a db with tables but no migration log) and `openEngineStore(file)`: tables `conversations`, `messages`, `grants`, `sessions`, `spend`, `audit` (Drizzle schema in `src/schema/`, migrations generated into `src/migrations/` by `bun run db:generate:engine`). `messages.recent` = last N oldest first; `grants.list` = the bot's grants plus `*`; `spend.add` increments. Imports only core, drizzle, `bun:sqlite`, node (`test/boundary.test.ts`). The engine db is `data/engine.db`.
- **Config dir** (`config`): `bots/<id>.md` (YAML header: name (one word), title, model, tools, skills, subagents, workspaces, autonomy, avatar (a name: `<AGENT_HOME>/config/avatars/<name>.png`, else `public/avatars/<name>.png`; the bot then speaks through its own webhook with that picture); body = instructions), `groups/<id>.yaml` (name, members, entryBot, `workspaces` (absolute paths, unique; the first is the main project), `instructions` (owner text)), `settings.yaml` (autonomy level, per-bot levels, per-tool outcomes, limits over the core defaults), `tools.yaml` (tool annotations). `mcp.yaml` (external MCP servers), `settings.yaml` also holds `projectsDir` and `memory.providers`; every key with its default is in `packages/config/defaults/settings.example.yaml` (a test keeps it in step with the schema and the core limits). Shipped defaults in `packages/config/defaults/` (annotations of the built-in SDK tools, the read-only Playwright tools, the memory and effect tools; Playwright in `mcp.yaml`; level `balanced`); the user dir wins by id / tool name.
- **Bad files:** each file is parsed alone; one that fails is listed in `problems` with its path and the rest loads. On a reload a file that fails but parsed before (a half-written save) keeps its last good copy. Files with the wrong extension (`.yml`), a typo'd `autonomy.bots` key, and limits a timer or query cannot use (fractions, over 2^31-1 ms) are reported too. After the merge a bot with a repeated name and a group naming a missing bot are dropped with a problem.
- **Live:** `FileConfig` serves bots, groups, the tool catalog, `settings()` and `limits()` from the current snapshot; `reload()` swaps the snapshot in one assignment and returns the changed or removed bots (they get a fresh session) and `changedGroups` (a group removed or whose workspaces changed); `watch()` reloads on file changes (debounced). A failed reload keeps the last good snapshot.
- **Not built:** retention of messages and audit.

## `packages/runtime-claude` (plan 3)
`AgentRuntime` on the Claude Agent SDK. Imports only `@friday/core`, the SDK and node (`packages/runtime-claude/test/boundary.test.ts`); never reads `process.env` (the caller passes the env).
- **Session** (`session/`): one long-lived streaming `query()` per bot; `ClaudeRuntime.open` returns at once with a UUID it hands the SDK as `sessionId` (it does not wait for `init`), `resume` passes `resume`. `send` pushes a formatted turn (`format-turn.ts`) into the input queue; `events` maps SDK messages (`map-message.ts`): bot text, `task_started`, `task_done` (completed / failed / stopped), `turn_end(cost)`, `error`. An error result is never a `turn_end`; a stream failure throws from `events`; `stop()` closes the input, aborts the SDK and ends `events`.
- **Options** (`build-options.ts`): `settingSources: []`, permission mode `default`, subagents as `background: true` agents, the bot's workspaces as cwd and extra dirs, a scrubbed env that does NOT set `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS`, the OS sandbox, a PreToolUse hook and `canUseTool` that both apply the hard floor first (the CLI auto-allows reads inside the bot's dirs without calling `canUseTool`, the hook covers them); `resume` throws when the SDK has no transcript left (the hub then opens a fresh session). The floor (`floor-check.ts`: file tools outside the bot's dirs, inside the agent home or on a sensitive file are denied and `decide` is never called), then `spec.decide` with `taskId` = the SDK `agentID` (a throw is a deny).
- **Floor** (`floor/`, moved from `src/`): OS sandbox builder, env scrub and deny list, sensitive paths, path helpers, sandbox errors. Safety floor = code, not data. 
- **Not verified live:** that `agentID` equals the `task_id` of `task_started`; that the session id stays the same after `resume`; background tasks under a long-lived session. Check with `scripts/smoke-runtime-claude.ts`.

## `packages/surface-discord` and `apps/friday` (plan 5)
`Surface` on Discord, and the composition root. Only `src/discord-js-port.ts` and `src/private-overwrites.ts` import `discord.js` (`packages/surface-discord/test/boundary.test.ts`); everything else talks to the `DiscordPort` interface, which tests fake.
- **Channels:** one private channel per bot and per group under a `Friday` category (the category is found by name, created once). The topic `friday:bot:<id>` / `friday:group:<id>` is the mapping; the channel id is the conversation id. `syncChannels` reuses a channel by topic, creates the missing ones (a failure on one is reported, the rest go on) and leaves channels of removed bots alone. Private = `@everyone` cannot view; the owner and the app can.
- **Messages:** only the owner's non-empty messages in mapped channels count; bots and webhooks are ignored. Bot text goes out through one webhook per channel (named `Friday`, cached) under the bot's name; system text and long text are split at 2000 chars (line, then space, then hard cut). Typing is shown while a bot works.
- **Approvals:** a card with buttons `Allow once`, `Always allow` (omitted for irreversible tools), `Deny`; only the owner's click on an open card of that channel settles it, the card is edited with the answer and loses its buttons. Open cards are cancelled on stop.
- **Commands:** guild slash commands `/status`, `/stop [bot]` and `/purge` (empties the trash), owner only. `/stop` without a name stops the channel's bot (or every member of a group).
- **App (`startApp`):** loads `FileConfig` (defaults + `<AGENT_HOME>/config`), opens `<AGENT_HOME>/data/engine.db`, builds the surface, `PermissionGate` and `BotHub`, syncs channels (new channels get `Ready. Talk to me here.` / `Group ready: @A, @B`), watches the config dir: a changed or removed bot is stopped and all its stored session ids cleared (`clearBot`; fresh session on its next message), a changed group's sessions are stopped and their stored ids cleared (`stopGroup`, `clearGroup`), then the channels are synced again, so a new bot or group gets a channel without a restart. A sweep every 60 s closes idle sessions. Sync and reload errors are logged, never thrown.
- **Friday bot:** shipped as a default bot file; it designs bots, groups, skills and MCP servers for the owner. It has `Read` but no `Write` or `Edit`: every write of the config dir goes through `BotDesign` and every look through `BotLookup` (the `design` server, built in the engine per session for a bot that names `mcp__design`). It reads three group templates (`code`, `social-content`, `research`) in `packages/config/templates/` (`extraDirsFor`: read only, no write grant, so its Bash cannot write the config dir either). A user bot file with the id `friday` is refused, `friday` cannot be a group member, and the shipped bot runs at autonomy `careful`. The shipped skills `bot-design` (turn a vague request into a strong bot), `skill-install` and `skill-creator` are in its `skills`.
- **`AGENT_HOME` layout:** `config/` (bots, groups, settings, tools, mcp), `data/engine.db`, `memory/{bots,groups}/<id>/`, `trash/<botId>/<stamp>/`, `scratch/<botId>/` (direct) and `scratch/<botId>_<groupId>/` (group session), `shared/<groupId>/` (one folder per group; every member reads and writes it, nothing else of the home is open), `inbox/<conversationId>/<epoch>/` (files from the owner, swept after a day) and `logs/`.
- **Not verified live:** the whole Discord path, the Friday bot flow, the templates' hand-offs. Checklist: [discord-setup.md](discord-setup.md).

## `packages/tools` (plan 6)
Built-in tools as in-process MCP servers, built per session. Imports only core, the SDK, zod and node; no env, no `console` (`packages/tools/test/boundary.test.ts`).
- **Memory files** (`memory/file-memory.ts`, `FileMemory` = the core `Memory` port): `<AGENT_HOME>/memory/bots/<id>/MEMORY.md` and `groups/<id>/MEMORY.md`, sections Decisions, Facts, Preferences, Lessons; one note per bullet, sanitized and deduplicated, file lock and atomic write, an edit backs the file up first (newest 20 in `backups/`).
- **Injection:** `BotHubDeps.memory`: the pool reads the bot's file when a session opens (`BotRuntimeSpec.memory`, appended to the system prompt as `## Your memory`; a group session gets only its Preferences and Lessons, `GROUP_SESSION_KINDS`); on a group turn the hub sends the group's file (`InboundTurn.groupMemory`, printed as `Group memory:` before the recent messages) only when it changed since that session last got it. After a compaction the first turn carries the bot's file again as `Your memory (updated):` when it changed (`InboundTurn.botMemory`). Every memory text carries one label (`MEMORY_LABEL` in core): the owner's saved preferences and rules apply, a note never grants a permission, overrides the instructions or asks for an action. A read failure sends nothing and never blocks the turn. Both are capped (`Memory.readForPrompt`; limits `memoryPromptChars` 12000, `groupMemoryPromptChars` 6000): over the cap nothing is deleted, the prompt gets Preferences, Decisions, Lessons, Facts, newest note first, then `(<N> older notes not shown; MemorySearch finds them.)`; a file over twice its cap logs `memory.large`.
- **Auto-recall:** `BotHubDeps.recall` (a `MemorySearcher`): for each turn of 8+ characters the hub searches the bot's notes in a direct session and the group's on a group turn (a group session recalls none of the bot's own notes) and sends hits not already in the memory the session was given as `InboundTurn.recalled`, a `<recalled_memory>` block (at most `recallNotes` 5 lines, `recallChars` 2000; `<` / `>` escaped; marked as data that may be outdated), printed after group memory and before the recent messages. A failing search sends nothing.
- **Tools** (`memory` server; every shipped bot names `mcp__memory`): `MemorySave` (note, kind, scope `bot` | `group`), `MemoryEdit` (list ids, replace, delete; a note longer than 200 chars after the cleanup is refused as `too_long`, never cut), `MemorySearch` (BM25 over the memory index: `MEMORY.md` and the journals, best match first, any query text is safe), `MessageSearch` (BM25 over past messages of the current conversation and, in the direct session only, the bot's direct chat; lines `[YYYY-MM-DD HH:MM author] text`). In a group session (`ToolSessionContext.groupId`) `MemorySearch` / `MemoryEdit` with scope `bot` see only the bot's Preferences and Lessons (no journal lines). Group scope only from a group conversation the bot is a member of (`ToolSessionContext.conversation()` follows `spec.currentConversation()`).
- **Memory index** (`memory/recall/`, `openMemoryIndex` in `store-sqlite`): a disposable SQLite db `<AGENT_HOME>/data/memory-index.db` (FTS5, `unicode61 remove_diacritics 2`, `đ` folded to `d`, so "trien khai" finds "triển khai") that mirrors the memory files, one chunk per bullet. `Indexer` rewrites a doc only when the sha256 of its file changed and removes docs whose file is gone; it runs after every `MemorySave` / `MemoryEdit` (`FileMemory` `onChange`), after a flush, and at start and daily after the journal prune (`reconcileAll`). A damaged or older-version db is deleted and rebuilt from the files; an indexing failure is logged (`memory.index`) and never fails a save. `MemoryRecall` asks every `RecallSource` in parallel (3 s limit, a failing source is skipped, fused by reciprocal rank): the builtin source, plus one source per provider plugin named in `settings.yaml` `memory.providers`. The same db holds a `messages` table (FTS5) filled from `engine.db` by `catchUpMessages` (`Store.messages.after(id)`; at start, log `memory.messages.ready`, and before every `MessageSearch`), so `engine.db` needs no migration. Core ports: `RecallSource`, `MemoryIndexStore`, `MessageIndexStore`, `MemorySearcher`. Design: [memory v2](superpowers/specs/2026-10-24-memory-v2-design.md).
- **Memory providers (optional plugins):** a `MemoryProviderPlugin` (core port: `id`, `secretEnv`, `parseOptions`, `check`, `create`) turns a `memory.providers` entry into a `RecallSource`; the app lists plugins in `apps/friday/src/memory-plugins.ts` (`MEMORY_PLUGINS`, one line each). Secrets come only from the env named in `secretEnv`; an unknown id, bad options or a failed `check` is a `config.problem` and the provider is skipped. When a source can `write`, memory is a `WriteThroughMemory` (`FileMemory` first, then the saved note to each source in order; an edit forgets the old text and writes the new; a failed provider call is tried again after 1 s, 5 s and 30 s unless Honcho rejected the request itself (`PermanentSourceError`, a 4xx other than 408 and 429), then logged as `memory.provider` with the attempts and dropped; it never fails the save; the queue keeps its order while a call retries; `stop()` ends the waits and drains the queue). First plugin: Honcho (`packages/memory-honcho`; conclusions per `bot-<id>`/`group-<id>` peer about `friday-owner`, search by `conclusions/query`, no LLM). Setup: [honcho-setup.md](honcho-setup.md).
- **Journal and flush:** `journal/<YYYY-MM-DD>.md` per owner (300 lines a day). After the SDK compacts a bot's main thread, `ClaudeRuntimeConfig.onCompact` hands the summary to `extractNotes` (one Haiku call, no tools, SDK structured output checked by the zod schema `ExtractedNotes` in `note-output-schema.ts` (up to 3 turns, so the SDK can ask again after a mismatch), at most 5 notes, 2 minute limit; the input is wrapped as `<summary>` with today's date, prompt in `extract-notes-prompt.ts`) and the notes go into today's journal as a `Flush` block, never into `MEMORY.md`; it never delays the bot. When a session is closed for being quiet, `BotHubDeps.onIdleClose` (`idleFlush` in the app) sends the messages of its conversations since it opened (2 or more, last 20000 chars) to `extractNotes` as a `<transcript>` and writes an `Idle flush` block. A group session writes both into the group's journal. A journal note over 200 chars is cut at a word and ends with `…` (`memory.journal_cut`); a full day file drops the block and logs `memory.journal_full`.
- **Consolidation and prune** (at start, not awaited, and daily): `consolidateAll` sends each owner's journal notes of complete days after its mark (`journal/.consolidated`, at most a full day file: 300 notes) to `consolidateNotes` (one Haiku call with today's date and the memory as numbered notes `[n] (kind) text`, prompt in `consolidate-notes-prompt.ts`; structured output checked by `PromotedNotes`; at most 5 `{kind, note, replaces?}`, default `{"notes": []}`; an answer of the wrong shape counts as no answer), saves them into `MEMORY.md` after `worthKeeping` (a pick with `replaces: n` edits note n in place with a backup, at most 3 a run) (a note under 10 characters, or with 80% of its words shared with a kept note, is skipped and counted; a duplicate is skipped too) and moves the mark only when the call answered. `pruneJournals` then deletes a day older than 30 days only when the mark has passed it, and any day older than 90; then `reconcileAll`.
- **Effects** (`effects` server, only for a bot that names one of its tools): `DeletePaths` (to `<AGENT_HOME>/trash/<botId>/<stamp>/`, 7 days, every path checked first: absolute, real path strictly inside a workspace, no `.git`, not sensitive; one refusal moves nothing), `GitPush` (`git push <remote> <b>:<b>`, never forced), `CreatePullRequest` (`gh pr create`), `MergeBranch` (refuses a dirty worktree, aborts a conflict), `CreateProject` (`git init` under `projectsDir`; the Friday bot only). Names must be plain (`isPlainName`); commands run as argv, no shell, with a minimal env (PATH, HOME, ssh agent, gh token); git runs with hooks off and refuses a repo whose local config sets a key that runs a program (fsmonitor, filters, merge drivers, sshCommand, includes...). A bot gets only the effect tools it names (`mcp__effects` = all). A dir is deleted only when nothing inside is sensitive or a nested repo; a symlink is refused (name its target). `mcp.yaml` is read again for every new session. A background task cannot use group scope while the bot answers another conversation; after a compaction the group memory is sent again. Annotations in `tools.yaml` decide asking: `DeletePaths` and `MergeBranch` destructive, `GitPush` and `CreatePullRequest` open-world.
- **External MCP servers** are data (`mcp.yaml`, stdio or http, `${NAME}` from the env); a bot names their tools as `mcp__<server>__<tool>` and the runtime denies any MCP tool a bot does not name.
- **Not verified live:** the flush, the idle flush, consolidation, auto-recall, the effect tools, Playwright through the new engine.

## Skills and shared folders
- **Skills:** `skills: [name]` in a bot file. At session open `buildSkillsPlugin` copies only those skills into `<scratch>/<botId>/skills-plugin/skills/<name>/` (a group session builds it under `<botId>_<groupId>`) (owner dir first, then the shipped `packages/config/defaults/skills/`; `.agents/skills/` is for developing this repo only) with a `.claude-plugin/plugin.json` named `friday`; the SDK gets `plugins: [{type: "local", path}]` and `skills: ["friday:<name>"]`, and `Skill` is added to the bot's tools. `Skill` is annotated read-only in `tools.yaml`. Not verified live.
- **Group workspaces (not verified live):** one session per bot and conversation scope, keyed `<botId>` (direct) or `<botId>@<groupId>` in the existing `sessions` table (the `bot_id` column holds the key; no migration, old rows stay valid as direct sessions). A group session runs with `bot.workspaces` = the group's workspaces (cwd = the first; none = its scratch dir); the sandbox, effect tools and `PostFile` follow. Scratch is per session (`_` in the group name: ids never contain it, `@` in the SDK sandbox layer is unverified). `FileConfig.reload()` returns `changedGroups` (workspaces changed or group removed): a changed bot clears all its sessions, a changed group stops and clears its sessions; editing only a group's `instructions` restarts nothing. `scopeBot` adds roster and shared-dir text per scope (direct: every group's; group: that group's only; `extraDirsFor` likewise). Every group turn carries a `Group context:` block (instructions, working dir and workspaces, project rules, a note to keep lasting project knowledge in the project's own files), sent when changed and after a compaction. Project rules = `CLAUDE.md`, else `AGENTS.md`, of the first workspace, read every group turn by `readProjectRules` (injected `ProjectRulesReader`, core reads no files), cut at 8 000 chars, symlinks skipped, wrapped as written by the project, not the owner. `/stop` in a group channel stops that group's sessions, `/stop @name` every session of the bot; `/status` lists one line per session. Limits: the direct session still reads every group's shared folder; a ticket wake always opens the direct session; the spend cap is per bot (two parallel turns can both pass); `MEMORY.md` and the journal are per bot (last write wins), a group session sees only the bot's Preferences and Lessons and writes its flushes to the group journal; `SetEffort` is per session; a group session and the direct chat do not share cwd, sandbox or scratch; plain `/stop` in a group channel replies naming every member, even those with no running session (only that group's sessions stop); a member removed from a group keeps its open session until the idle sweep or `/stop`; the `BotDesign` workspace check is lexical (symlinks and ancestors of the agent home are caught by the sandbox/floor).
- **Shared folder per group:** `<AGENT_HOME>/shared/<groupId>/`, read-write for every member (`extraDirsFor`), named in each member's instructions.

## Files in both directions (plan 7)
- **From the owner:** `DiscordSurface` (given `{ inboxDir, now }`) downloads the files of the owner's message before the hub sees it: at most 5, 20 MB each (declared size and bytes read), name = last path part with `[^A-Za-z0-9._-]` replaced by `_`, cut to 100 chars, prefixed `<n>-`, written with `wx` under `<AGENT_HOME>/inbox/<channel>/<epoch>/`. Non-owner, bot and webhook messages are dropped before any download. A refused file is named in a system reply. A message with only files counts. The core `InboundMessage.attachments` reaches the `InboundTurn` of the turn that answers it, never a hand-off.
- **In the Claude runtime:** a turn with files becomes content blocks: one text block (the turn plus an `Attached files:` list) and one base64 image block per png / jpeg / gif / webp up to 5 MB. Any other file, or a bigger image, is copied into `<scratch>/<botId>/inbox/t-<random>/` (a group session: `<scratch>/<botId>_<groupId>/inbox/...`) and listed by path, so the bot reads it with `Read`.
- **Thinking effort:** the bot file's `effort` goes to the SDK `effort` option (a subagent's too). `SetEffort` (`chat` server, named in the bot's `tools`) lets a bot change its own level mid-session through `EffortControl` on the spec (the runtime fills `apply` with `Query.applyFlagSettings`), never above the file's `maxEffort`; a new session starts at `effort`.
- **To the owner:** `PostFile` (`chat` server, every bot): a regular file (no link) strictly inside the bot's workspaces or its scratch dir, not sensitive, not under a git dir, at most 8 MB, sent through `Surface.postFile` (a webhook post with the file) to the conversation of the turn in progress, under the bot's name. Refused between turns.
- **Git runner:** every git call runs with `GIT_HARDEN` pins and `GIT_RUN_ENV` (`GIT_CONFIG_GLOBAL` and `GIT_CONFIG_SYSTEM` set to `/dev/null`, no terminal prompt), so the owner's global git config does not apply; the owner's name and email come in as `GIT_AUTHOR_*` / `GIT_COMMITTER_*` env.

## Next
- An own web app replaces Discord (a second `Surface` adapter; see [ports/surface.md](ports/surface.md)).
- **Design tools** (`packages/tools/src/design`): `BotDesign` actions `write_bot`, `write_group`, `write_skill`, `install_skill`, `set_mcp`; no action takes a path from the model. Fields are checked (ids, tools in the catalog or a known MCP server, skills that exist, workspaces that are existing dirs outside the agent home, no literal secret in an MCP env), the app's parsers (`parseBotFile`, `parseGroupFile`, `parseMcpFile`, injected through `DesignContext`) accept the text, and the file is written in one step. `install_skill` copies a skill dir the bot cloned into its own scratch dir (no links, no VCS dir, at most 100 files and 2 MB; nothing in it is run) and records source and commit in `config/skills/skills.lock.yaml`. `BotDesign` is annotated destructive, not idempotent, open-world: it asks at every autonomy level and never offers "Always allow". Its scope keys (`action`, `id`, `overwrite`, `autonomy`, `server`, `tools`, `workspaces`...) put what will be written on the approval card (cut at 1200 chars). A bot or group file that exists is replaced only with `overwrite: true` (a bot keeps its `subagents`); `autonomy: autonomous` and the design tools themselves cannot be written into a bot file, and the design server is built for the Friday bot only; an MCP `${NAME}` reference is allowed only in `env` and `headers` and never names an engine secret (`CLAUDE_CODE_*`, `ANTHROPIC_*`, `DISCORD_*`). `BotLookup` (read-only) lists bots, groups, skills with descriptions, MCP servers and tool names, and reads one bot file or skill.
