# Friday System Architecture

Last updated: 2026-10-27 (memory quality: own-turn flush, `<known>`, group note routing, near-duplicate refusal, post-flush consolidation: not verified live; engine plans 1-7 and web app plans 1-6 done: the engine runs on the web surface with memory, effect tools, files in both directions, R2 storage and no leftover engine code; plus durable multi-worker runs and owner and bot communication: not verified live). Target designs: team engine, web app, durable runs.

## Now
- `bun run start` (`apps/friday/src/index.ts`) checks the config and the credential (`CLAUDE_CODE_OAUTH_TOKEN`), refuses an `AGENT_HOME` inside a git working tree, creates the home, starts the trash and home-retention sweepers, then runs the engine (`startEngine` in `apps/friday/src/main.ts`): it refuses by name (`WEB_ORIGIN missing`, `PUBLIC_API_URL missing`, `AUTH_SECRET missing`, `OWNER_EMAIL missing`, `R2_ACCOUNT_ID missing`, `R2_ACCESS_KEY_ID missing`, `R2_SECRET_ACCESS_KEY missing`, `R2_BUCKET missing`) before any network call, builds `R2FileStore`, `WebSurface`, `ClaudeRuntime` and `startApp`, starts the API (Hono on `127.0.0.1:API_PORT`, default 8787), logs `engine.started` and runs until SIGINT / SIGTERM (then `app.stop()`, the API server and the sweepers stop). Env keys: `CLAUDE_CODE_OAUTH_TOKEN`, `AGENT_HOME`, `LOG_LEVEL`, `API_PORT`, `WEB_ORIGIN`, `PUBLIC_API_URL`, `AUTH_SECRET` (at least 32 characters), `OWNER_EMAIL`, `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET`, optional `CDN` (`src/config/agent-config.ts`). The auth secret and the R2 keys are on the env-deny list for bots.
- `src/` holds only the process entry: `index.ts`, `lifecycle/` (boot, boot checks, home placement check, main lock, trash and home-retention sweepers), `config/` (env, home paths, model ids), `observability/` (pino logger and log files).
- Removed: chief-of-staff / worker / goal / plan engine, the Discord surface (its package, channel sync, webhooks and slash commands; `/status`, `/stop` and `/purge` are `control` routes now), the old SQLite db and its migrations, presets and roles as files, the old MCP servers, artifacts store and viewer, ops dashboard, dreaming and episodes. Data of older builds in `AGENT_HOME` is ignored, never opened or deleted; at boot the engine deletes conversations keyed by Discord channel ids and their messages.

## `packages/core` (plan 2)
Domain, ports and use cases; no dependencies, imports only itself (`packages/core/test/core-boundary.test.ts`). Ports are in [`packages/core/src/ports/`](../packages/core/src/ports/): `AgentRuntime` (+ `BotSession`, generic `RuntimeEvent`), `Surface`, `Store`, `ToolCatalog`, `Memory`, `Clock`.
- **Routing** (`routing/`): `@name` parsing; direct chat goes to its bot, a group message to the mentioned members or the entry bot, a bot reply wakes no one: bots reach each other only through the `SendToBot` and `HandOff` tools (`BotMessenger`). `ChainGuard` caps hops, bot messages per hour and bot repeats.
- **Permission** (`permission/`): `decide` is pure (full order in Owner and bot communication): hard-floor deny, tool override, taint, owner rule, then the autonomy level (careful / balanced / autonomous) for the tool's class from its annotations. Unannotated = ask; irreversible = ask always (no "Always allow"). `PermissionGate` asks through the `Surface`, stores grants and audits; an approval has no timeout (it is a stored card, see Durable runs).
- **Hub** (`hub/`): `BotHub` is the intake: it routes a message, stores every bot-to-bot wake as a run in the `wakes` table, keeps the shared ticket board (`TicketBoard`: assigning a ticket wakes the assignee; a ticket left open after a turn gets one re-wake, then is blocked; a ticket keeps the group it was created in, `Ticket.groupId`, immutable, and a follow-up ticket made inside a group or ticket session keeps the session's group; a group ticket is assigned only to a member of its group, else `not_member`, from tools and from the web API), returns a finished request to its sender as a `result`, applies the daily spend cap and serves `stop` and `status`. It holds no session: runs execute in `runs/` (see Durable runs). There is no queue per session and no idle session close.
- Defaults: `packages/core/src/config-defaults.ts`.

## `packages/store-sqlite` and `packages/config` (plan 4)
Bots and groups are files; the db holds the rest. `apps/friday` joins them: `{ ...engineStore, bots, groups: config.groups }` is the core `Store` (the Friday bot gets its real dirs filled in).
- **Engine db** (`store-sqlite`): `openEngineDb(file)` (WAL, owner-only file and sidecars, refuses a db with tables but no migration log) and `openEngineStore(file)`: tables `conversations`, `messages`, `grants`, `sessions`, `spend`, `audit` (Drizzle schema in `src/schema/`, migrations generated into `src/migrations/` by `bun run db:generate:engine`). `messages.recent` = last N oldest first; `grants.list` = the bot's grants plus `*`; `spend.add` increments. Imports only core, drizzle, `bun:sqlite`, node (`test/boundary.test.ts`). The engine db is `data/engine.db`.
- **Config dir** (`config`): `bots/<id>.md` (YAML header: name (one word), title, model, tools, skills, subagents, workspaces, autonomy, avatar (a name: `<AGENT_HOME>/config/avatars/<name>.png`, else `public/avatars/<name>.png`; or `upload:<id>` for a picture uploaded in the web app); body = instructions), `groups/<id>.yaml` (name, members, entryBot, `workspaces` (absolute paths, unique; the first is the main project), `instructions` (owner text)), `settings.yaml` (autonomy level, per-bot levels, per-tool outcomes, limits over the core defaults), `tools.yaml` (tool annotations). `mcp.yaml` (external MCP servers), `settings.yaml` also holds `projectsDir` and `memory.providers`; every key with its default is in `packages/config/defaults/settings.example.yaml` (a test keeps it in step with the schema and the core limits). Shipped defaults in `packages/config/defaults/` (annotations of the built-in SDK tools, the read-only Playwright tools, the memory and effect tools; Playwright in `mcp.yaml`; level `balanced`); the user dir wins by id / tool name.
- **Bad files:** each file is parsed alone; one that fails is listed in `problems` with its path and the rest loads. On a reload a file that fails but parsed before (a half-written save) keeps its last good copy. Files with the wrong extension (`.yml`), a typo'd `autonomy.bots` key, and limits a timer or query cannot use (fractions, over 2^31-1 ms) are reported too. After the merge a bot with a repeated name and a group naming a missing bot are dropped with a problem.
- **Live:** `FileConfig` serves bots, groups, the tool catalog, `settings()` and `limits()` from the current snapshot; `reload()` swaps the snapshot in one assignment and returns the changed or removed bots (they get a fresh session) and `changedGroups` (a group removed or whose workspaces changed); `watch()` reloads on file changes (debounced). A failed reload keeps the last good snapshot.
- **Not built:** retention of messages and audit.

## `packages/runtime-claude` (plan 3)
`AgentRuntime` on the Claude Agent SDK. Imports only `@friday/core`, the SDK and node (`packages/runtime-claude/test/boundary.test.ts`); never reads `process.env` (the caller passes the env).
- **Session** (`session/`): one long-lived streaming `query()` per bot; `ClaudeRuntime.open` returns at once with a UUID it hands the SDK as `sessionId` (it does not wait for `init`), `resume` passes `resume`. `send` pushes a formatted turn (`format-turn.ts`) into the input queue; `events` maps SDK messages (`map-message.ts`): bot text, `task_started`, `task_done` (completed / failed / stopped), `turn_end(cost)`, `error`. An error result is never a `turn_end`; a stream failure throws from `events`; `stop()` closes the input, aborts the SDK and ends `events`.
- **Options** (`build-options.ts`): `settingSources: []`, permission mode `default`, subagents as `background: true` agents, the bot's workspaces as cwd and extra dirs, a scrubbed env that does NOT set `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS`, the OS sandbox, a PreToolUse hook and `canUseTool` that both apply the hard floor first (the CLI auto-allows reads inside the bot's dirs without calling `canUseTool`, the hook covers them); `resume` throws when the SDK has no transcript left (the hub then opens a fresh session). The floor (`floor-check.ts`: file tools outside the bot's dirs, inside the agent home or on a sensitive file are denied and `decide` is never called), then `spec.decide` with `taskId` = the SDK `agentID` (a throw is a deny).
- **Floor** (`floor/`, moved from `src/`): OS sandbox builder, env scrub and deny list, sensitive paths, path helpers, sandbox errors. Safety floor = code, not data. Bash reads: the home and `/Users` are denied around the granted dirs (`denyAround`), not whole with the grants allowed back, so a repo root that holds a `.env` stays listable while the `.env` stays denied; the dirs on the way to a grant show their entry names; a deny list is a snapshot at session start; too deep or unreadable fails closed. Env templates (`.env.example`, `.env.sample`, `.env.template`) are not sensitive (`except` in `sensitive-paths.yaml`). 
- **Not verified live:** that `agentID` equals the `task_id` of `task_started`; that the session id stays the same after `resume`; background tasks under a long-lived session. Check with `scripts/smoke-runtime-claude.ts`.

## `packages/contracts` and `packages/api`
- **`contracts`:** the oRPC contract, zod DTOs, `FridayEvent` and limits; the only code the web app and the API share. Imports only `@orpc/contract` and `zod` (`packages/contracts/test/boundary.test.ts`).
- **Routes** (`packages/api/src/app.ts`): `/health` (engine up, db reachable), `/api/auth/*` (better-auth: the owner user is created at boot, sign-up off, magic link for first login and recovery written to the owner-only `<AGENT_HOME>/logs/owner-links.log`, passkey for normal login), `/rpc/*` (oRPC, every procedure needs the owner session). Middleware order: request log, CORS for the one `WEB_ORIGIN` with credentials, `Origin` check on non-GET requests, then the session check (`auth.api.getSession`, only `OWNER_EMAIL` passes) before `/rpc/*`.
- **Routers** (`src/rpc/router.ts`): `conversations` (list, messages page, `markRead`), `chat` (`uploadCreate`, `send`, `file`, `files`), `approvals`, `questions`, `control` (`status`, `stop`, `purge`, `toolCheck`), `tickets` (through `TicketBoard`, the owner as actor), `ops` (sessions, wakes, spend), `memory`, `schedules` (list, get, runs, create, update, setEnabled, runNow, delete; through `ScheduleBoard`, the owner as actor), `events` (SSE `subscribe`, heartbeat every 25 s) and `config` (`bots`, `groups`, `avatars`, `owner`, `skills`, `mcp`).
- **Settings admin** (web plan 5): the API calls the core ports `ConfigAdmin`, `SkillAdmin`, `MemoryAdmin` and `McpProbe` (`packages/core/src/ports/settings-admin.ts`), implemented in `packages/tools/src/admin/` and composed in `apps/friday/src/settings-admin.ts`. Saves use the parsers `BotDesign` uses and write only inside `<AGENT_HOME>/config/` and `<AGENT_HOME>/memory/`; the config watcher reloads them.
- **Boundary:** `api` imports `contracts`, `core`, `surface-web`, `hono`, `@orpc/*`, `better-auth` and node only; never `runtime-claude` or `store-sqlite`; no env, console or wall-clock calls (`packages/api/test/boundary.test.ts`). Errors are oRPC typed errors (`UNAUTHORIZED`, `NOT_FOUND`, `CONFLICT`, `BAD_REQUEST`, `PAYLOAD_TOO_LARGE`).

## `packages/surface-web`
`WebSurface implements Surface`; no HTTP code.
- **Event bus** (`event-bus.ts`): every `FridayEvent` gets an increasing id; the last 500 are kept in memory and replayed from `lastEventId`; an id that is gone gets `resync`. No event table: messages are already stored.
- **Messages and cards:** `post` stores nothing itself (the hub does) and publishes a `message` event with a `MessageDto` (author, text, files, `replyTo`, relay cards for `SendToBot` / `HandOff`). Approval cards and question cards (`card-desk.ts`) are rows that stay open until answered or withdrawn (no timeout, see Cards below); the first answer wins, later answers get `CONFLICT`; open cards stay open across a restart and are shown again.
- **Run steps:** `showRun` publishes `run` events (thinking, tool, skill, mcp, subagent, command, writing); on turn end the steps are stored in `messages.run`.
- **Inbound:** `chat.send` is the only way a message enters (`replyTo` supported); the upload is checked (`stat`; the type is decided by the file extension from a fixed list, an image also by its first bytes) and copied to `<AGENT_HOME>/inbox/<conversationId>/<epoch>-<id>/` for the bot. `postFile` stores the file through `FileStore` and writes a `files` row and a message.
- **Reading office files:** the shipped skill `office-files` reads docx and xlsx through `uvx` with `markitdown`, and a PDF with `Read` or `pdftotext`. Only bots that list `office-files` in `skills` (and have `Bash` and `Read`) read Office files; any other bot must be given the skill.
- **Boundary:** core, contracts (types only), `image-size` and node (`packages/surface-web/test/boundary.test.ts`).

## `packages/store-r2` and files
- `R2FileStore` implements the core `FileStore` port over `Bun.S3Client`; presigning is a local signature. Only this package talks to R2 (`packages/store-r2/test/boundary.test.ts`); `scripts/smoke-r2.ts` checks a real bucket.
- **Keys** (made by the engine, never by a client): `uploads/<conversationId>/<uploadId>/<name>`, `files/<conversationId>/<fileId>/<name>`, `avatars/<bots|groups>/<id>/<uploadId>.<webp|jpg>`.
- **Flow:** `chat.uploadCreate` checks count (5), size (20 MB) and type, records a pending `uploads` row and returns a presigned PUT (10 min); the type is decided by the extension (`ACCEPTED_FILE_TYPES` in `packages/contracts/src/file-types.ts`, kept equal to `packages/surface-web/src/accepted-types.ts` by a test): jpg, jpeg, png, gif, webp, pdf, csv, txt, md, json, docx, xlsx; any other name is refused by name; the browser PUTs straight to R2, so bytes never pass the tunnel. `chat.send` takes the upload ids, claims each (`pending` to `claimed`), `stat`s the object (too big: delete, `PAYLOAD_TOO_LARGE`), checks an image's type from its first bytes, marks it used and copies it to `inbox/` for the bot. `PostFile` puts the file (at most 8 MB) and writes a `files` row. Avatars follow the upload path with a 2 MB cap.
- **Show:** images go through `${CDN}/<key>` when the optional `CDN` custom domain is set (the web build reads it as `VITE_CDN_ORIGIN`); every other file, and images without `CDN`, use presigned GET URLs (15 min; avatars 1 h, expiry rounded so the URL stays stable). `chat.file` resolves by id only.
- **Library:** `chat.files` lists the owner's uploads (store `files.listUploads`, newest first, optional `kind` and `conversationId`, `limit` up to 100, opaque `nextCursor`); the web Files screen (`/files`) pages through it. A PDF previews in the browser with `react-pdf`, loaded lazily and kept out of the PWA precache; the viewer fetches the file from the R2 origin, so the bucket CORS must allow GET from `WEB_ORIGIN`.
- **Clean-up:** a sweeper deletes uploads left unused after a day with their objects. Used files stay with their message; no R2 lifecycle rule.

## `apps/friday` (plan 5, web composition)
The composition root. Boot sequence and the web API wiring are in Now and the sections above.
- **Tool check:** at boot `lifecycle/tool-check.ts` looks for `uvx` and `pdftotext` on PATH, logs one warning per missing tool (`tool.missing`) and never fails the boot. `control.toolCheck` returns the missing tools with an install hint; the web app shows them in a banner.
- **App (`startApp`):** loads `FileConfig` (defaults + `<AGENT_HOME>/config`), opens `<AGENT_HOME>/data/engine.db`, builds the surface, `PermissionGate` and `BotHub`, syncs conversations (`bot:<id>` and `group:<id>`, created when a bot or group appears in the config), watches the config dir: a changed or removed bot is stopped and all its stored session ids cleared (`clearBot`; fresh session on its next message), a changed group's sessions are stopped and their stored ids cleared (`stopGroup`, `clearGroup`), then the conversations are synced again, so a new bot or group gets a conversation without a restart. A sweep every 60 s closes idle sessions. Sync and reload errors are logged, never thrown.
- **Friday bot:** shipped as a default bot file; it designs bots, groups, skills and MCP servers for the owner. It has `Read` but no `Write` or `Edit`: every write of the config dir goes through `BotDesign` and every look through `BotLookup` (the `design` server, built in the engine per session for a bot that names `mcp__design`). It reads three group templates (`code`, `social-content`, `research`) in `packages/config/templates/` (`extraDirsFor`: read only, no write grant, so its Bash cannot write the config dir either). A user bot file with the id `friday` is refused, `friday` cannot be a group member, and the shipped bot runs at autonomy `balanced` (its config writes all go through `BotDesign`, which always asks). The shipped skills `bot-design` (turn a vague request into a strong bot), `skill-install` (attach, write with `references/skill-writing.md`, install by git clone into its scratch dir, add MCP servers), `find-skill` (search trusted repos, curated lists and skills.sh) and `bot-tuning` (review bots from their run log and propose fixes) are in its `skills`; the shipped `skill-creator` (Anthropic's, with eval scripts) is not, so its eval loop never conflicts with Friday's tools. `BotInsight` (design server, Friday only) reads the engine's own log through the `InsightStore` port (`store-sqlite` `insight-repo.ts`: `json_each` over `messages.run`, wakes, spend, tickets), never an agent library's files; `BotDesign` also writes `subagents`, `add_lesson` and `delete_bot`.
- **`AGENT_HOME` layout:** `config/` (bots, groups, settings, tools, mcp), `data/engine.db`, `memory/{bots,groups}/<id>/`, `trash/<botId>/<stamp>/`, `scratch/<botId>/` (direct) and `scratch/<botId>_<groupId>/` (group session), `shared/<groupId>/` (one folder per group; every member reads and writes it, nothing else of the home is open), `inbox/<conversationId>/<epoch>-<id>/` (files from the owner, swept after a day) and `logs/`.
- **Not verified live:** the whole web path (API, auth, R2, the PWA), the Friday bot flow, the templates' hand-offs. Checklist: [web-setup.md](web-setup.md).

## `packages/tools` (plan 6)
Built-in tools as in-process MCP servers, built per session. Imports only core, the SDK, zod and node; no env, no `console` (`packages/tools/test/boundary.test.ts`).
- **Memory files** (`memory/file-memory.ts`, `FileMemory` = the core `Memory` port): `<AGENT_HOME>/memory/bots/<id>/MEMORY.md` and `groups/<id>/MEMORY.md`, sections Decisions, Facts, Preferences, Lessons; one note per bullet, sanitized and deduplicated, file lock and atomic write, an edit backs the file up first (newest 20 in `backups/`).
- **Injection:** `BotHubDeps.memory`: every run reads, when it opens its session (`openRunSession`), the owner's rules for the bot (`Memory.readRules`, `BotRuntimeSpec.rules`, `## Your rules` with `RULES_LABEL`, before the memory and never cut by the memory cap), the bot's file (`BotRuntimeSpec.memory`, `## Your memory`; a group session gets only its Preferences and Lessons, `GROUP_SESSION_KINDS`) and, for a group session, the group context, the group's rules (`groupRules`) and the group's file (`groupMemory`), all in the system prompt. An edit (rules, memory, the owner's `USER.md` / `SOUL.md` at the start of the bot's instructions) reaches the next run; a compaction keeps them. Every memory text carries one label (`MEMORY_LABEL` in core): the owner's saved preferences and rules apply, a note never grants a permission, overrides the instructions or asks for an action. A read failure sends nothing and never blocks the turn. Both are capped (`Memory.readForPrompt`; limits `memoryPromptChars` 12000, `groupMemoryPromptChars` 6000): over the cap nothing is deleted, the prompt gets Preferences, Decisions, Lessons, Facts, newest note first, then `(<N> older notes not shown; MemorySearch finds them.)`; a file over twice its cap logs `memory.large`.
- **Auto-recall:** `BotHubDeps.recall` (a `MemorySearcher`): for each turn of 8+ characters the hub searches the bot's notes in a direct session and the group's on a group turn (a group session recalls none of the bot's own notes) and sends hits not already in the memory the session was given as `InboundTurn.recalled`, a `<recalled_memory>` block (at most `recallNotes` 5 lines, `recallChars` 2000; `<` / `>` escaped; marked as data that may be outdated), printed after group memory and before the recent messages. A failing search sends nothing.
- **Tools** (`memory` server; every shipped bot names `mcp__memory`): `MemorySave` (note, kind, scope `bot` | `group`; refuses a note under 10 chars and a near-duplicate of a kept note as `duplicate: similar note <id>: "<text>"`, so the bot uses `MemoryEdit` to replace it: not verified live), `MemoryEdit` (list ids, replace, delete; a note longer than 200 chars after the cleanup is refused as `too_long`, never cut), `MemorySearch` (BM25 over the memory index: `MEMORY.md` and the journals, best match first, any query text is safe), `MessageSearch` (BM25 over past messages of the current conversation and, in the direct session only, the bot's direct chat; lines `[YYYY-MM-DD HH:MM author] text`). In a group session (`ToolSessionContext.groupId`) `MemorySearch` / `MemoryEdit` with scope `bot` see only the bot's Preferences and Lessons (no journal lines). Group scope only from a group conversation the bot is a member of (`ToolSessionContext.conversation()` follows `spec.currentConversation()`).
- **Memory index** (`memory/recall/`, `openMemoryIndex` in `store-sqlite`): a disposable SQLite db `<AGENT_HOME>/data/memory-index.db` (FTS5, `unicode61 remove_diacritics 2`, `đ` folded to `d`, so "trien khai" finds "triển khai") that mirrors the memory files, one chunk per bullet. `Indexer` rewrites a doc only when the sha256 of its file changed and removes docs whose file is gone; it runs after every `MemorySave` / `MemoryEdit` (`FileMemory` `onChange`), after a flush, and at start and daily after the journal prune (`reconcileAll`). A damaged or older-version db is deleted and rebuilt from the files; an indexing failure is logged (`memory.index`) and never fails a save. `MemoryRecall` asks every `RecallSource` in parallel (3 s limit, a failing source is skipped, fused by reciprocal rank): the builtin source, plus one source per provider plugin named in `settings.yaml` `memory.providers`. The same db holds a `messages` table (FTS5) filled from `engine.db` by `catchUpMessages` (`Store.messages.after(id)`; at start, log `memory.messages.ready`, and before every `MessageSearch`), so `engine.db` needs no migration. Core ports: `RecallSource`, `MemoryIndexStore`, `MessageIndexStore`, `MemorySearcher`. Design: memory v2.
- **Memory providers (optional plugins):** a `MemoryProviderPlugin` (core port: `id`, `secretEnv`, `parseOptions`, `check`, `create`) turns a `memory.providers` entry into a `RecallSource`; the app lists plugins in `apps/friday/src/memory-plugins.ts` (`MEMORY_PLUGINS`, one line each). Secrets come only from the env named in `secretEnv`; an unknown id, bad options or a failed `check` is a `config.problem` and the provider is skipped. When a source can `write`, memory is a `WriteThroughMemory` (`FileMemory` first, then the saved note to each source in order; an edit forgets the old text and writes the new; a failed provider call is tried again after 1 s, 5 s and 30 s unless Honcho rejected the request itself (`PermanentSourceError`, a 4xx other than 408 and 429), then logged as `memory.provider` with the attempts and dropped; it never fails the save; the queue keeps its order while a call retries; `stop()` ends the waits and drains the queue). First plugin: Honcho (`packages/memory-honcho`; conclusions per `bot-<id>`/`group-<id>` peer about `friday-owner`, search by `conclusions/query`, no LLM). Setup: [honcho-setup.md](honcho-setup.md).
- **Journal and flush:** `journal/<YYYY-MM-DD>.md` per owner (300 lines a day). After the SDK compacts a bot's main thread, `ClaudeRuntimeConfig.onCompact` hands the summary to `extractNotes` (one Haiku call, no tools, SDK structured output checked by the zod schema `ExtractedNotes` in `note-output-schema.ts` (up to 3 turns, so the SDK can ask again after a mismatch), at most 5 notes, 2 minute limit; the input is wrapped as `<summary>` with today's date, prompt in `extract-notes-prompt.ts`) and the notes go into today's journal as a `Flush` block, never into `MEMORY.md`; it never delays the bot. When a session is closed for being quiet, `BotHubDeps.onIdleClose` (`idleFlush` in the app) sends the messages of its conversations since it opened (2 or more, last 20000 chars) to `extractNotes` as a `<transcript>` and writes an `Idle flush` block. In a group session the extraction answers `{note, about}` (`bot` | `group`) and a group flush sends only the bot's own turns (`ownTurns`: its messages and the owner lines it answered; other bots' lines are left out). Both calls also get `<known>` (`memory-known.ts`: the bot's instructions, which start with USER/SOUL, and the group's instructions; cut to `KNOWN_MAX_CHARS` 8000) so the model skips what config already says. `writeFlushNotes` puts `about: group` notes into the group's journal under `Flush` / `Idle flush` and the bot's own notes from a group into the bot's journal under `Flush @<groupId>` / `Idle flush @<groupId>`; a direct session writes everything to the bot's journal. Not verified live. A journal note over 200 chars is cut at a word and ends with `…` (`memory.journal_cut`); a full day file drops the block and logs `memory.journal_full`.
- **Consolidation and prune** (at start, not awaited, and daily): `consolidateAll` sends each owner's journal notes after its mark (`journal/.consolidated`, today's notes included, at most a full day file: 300 notes; the mark is `YYYY-MM-DD#n` = the first n notes of that day are done, an old plain `YYYY-MM-DD` means the whole day) to `consolidateNotes` with `<known>` (`ownerKnown`), as one Haiku call with today's date and the memory as numbered notes `[n] (kind) text`, prompt in `consolidate-notes-prompt.ts`; structured output checked by `PromotedNotes`; at most 5 `{kind, note, replaces?}`, default `{"notes": []}`; an answer of the wrong shape counts as no answer; the picks are saved into `MEMORY.md` after `worthKeeping` (a pick with `replaces: n` edits note n in place with a backup, at most 3 a run) (a note under 10 characters, or with 80% of its words shared with a kept note, is skipped and counted; a duplicate is skipped too) and moves the mark only when the call answered. For a bot, notes from blocks labelled `@<groupId>` are asked in a second call and a `fact` or `decision` picked from them is saved as a `lesson` (group sessions see only Preferences and Lessons). After each idle flush the owners it wrote are consolidated at once (`flushConsolidation`, not awaited, failure logged), through `createOwnerQueue` that serializes every consolidation per owner with the daily run; on stop a call still waiting on the model is given up (unanswered: nothing saved, mark stays) and the started runs are awaited before the memory closes. Not verified live. `pruneJournals` then deletes a day older than 30 days only when the mark has passed it (the mark day itself counts as passed only for an old plain mark; a `#n` mark day is kept), and any day older than 90; then `reconcileAll`.
- **Effects** (`effects` server, only for a bot that names one of its tools): `DeletePaths` (to `<AGENT_HOME>/trash/<botId>/<stamp>/`, 7 days, every path checked first: absolute, real path strictly inside a workspace, no `.git`, not sensitive; one refusal moves nothing), `GitPush` (`git push <remote> <b>:<b>`, never forced), `CreatePullRequest` (`gh pr create`), `MergeBranch` (refuses a dirty worktree, aborts a conflict), `CreateProject` (`git init` under `projectsDir`; the Friday bot only). Names must be plain (`isPlainName`); commands run as argv, no shell, with a minimal env (PATH, HOME, ssh agent, gh token); git runs with hooks off and refuses a repo whose local config sets a key that runs a program (fsmonitor, filters, merge drivers, sshCommand, includes...). A bot gets only the effect tools it names (`mcp__effects` = all). A dir is deleted only when nothing inside is sensitive or a nested repo; a symlink is refused (name its target). `mcp.yaml` is read again for every new session. A background task cannot use group scope while the bot answers another conversation; after a compaction the group memory is sent again. Annotations in `tools.yaml` decide asking: `DeletePaths` and `MergeBranch` destructive, `GitPush` and `CreatePullRequest` open-world.
- **External MCP servers** are data (`mcp.yaml`, stdio or http, `${NAME}` from the env); a bot names their tools as `mcp__<server>__<tool>` and the runtime denies any MCP tool a bot does not name.
- **OAuth MCP servers:** an http entry with `oauth: { scopes? }` (https url; an `Authorization` header is a parse error). `Sign in` (`config.mcp.signIn`) returns the provider URL (discovery, dynamic client registration, PKCE; one pending login per `state`, single use, 10 min); the API callback `GET /oauth/mcp/callback` stores the tokens in the engine db and redirects to `${WEB_ORIGIN}/settings/mcp/<server>?signin=ok` (or `/settings/mcp?signin=<denied|expired|failed>`). ## Durable runs and workers
Design: 2026-10-25-durable-multi-worker-runs-design.md. Not verified live.
- **Processes** (`apps/friday/src/workers/`): one main process (web API and surface, config watch, sweepers, intake, reconciler, supervisor) and `limits.workers` worker processes (default 2; `0` = in-process mode: the same run code in the main process, no children). The main process takes an exclusive lock `<AGENT_HOME>/data/main.lock` (pid; a stale pid is reclaimed) and exits 1 if another main holds it. `supervisor.ts` spawns workers (`worker-spawn.ts`), restarts a dead one with backoff and forwards hints; a worker exits when IPC disconnects. Each worker runs in its own process group; when a worker exits or is killed, main SIGKILLs that group, so its SDK child processes die with it; a worker that exits on its own (also when main was SIGKILLed) first sends SIGTERM to its own group. A graceful worker stop aborts its sessions, requeues its runs without counting a cut, waits up to 10 s for them to settle and hard-exits 5 s later; main SIGKILLs a worker still alive after 15 s. At start, a queued run that never started (no attempt, no card) and is older than 24 h is expired; a requeued, retrying or answered-card run is resumed.
- **IPC** (`ipc-protocol.ts`, zod-checked): main to worker `init` (config) and hints (new run, card answered, steering, cancel, config changed); worker to main hints, live events (typing, run steps, subagent) and surface calls. Rows are written first and the hint is only a speed-up: a worker scans for claimable runs every 5 s. Live events are not stored; a stored message that was posted over IPC and lost is found by a web refetch.
- **Runs** (`packages/core/src/runs/`): a run is a `wakes` row with a scope (`<botId>`, `<botId>@<groupId>` or `<botId>#ticket@<groupId>`). States: `queued -> leased -> running -> done | failed | cancelled`, `running -> waiting_input -> queued`, plus `blocked`, `interrupted`, `expired`, `dropped`. Every transition is one conditional update on state and lease fence; a write that matches no row means another worker owns the run. One active run per scope (`waiting_input` does not hold it); interactive before background, oldest first. Lease 5 min, heartbeat 60 s; a dead worker's run is claimed with fence + 1, and runs of an older boot are reclaimable at once. A claim writes an attempt row (`run_attempts`).
- **Intake** (`run-intake*.ts`, `run-supersede.ts`): a client nonce makes a resend return the first result. The steps are idempotent writes, not one transaction: the message is stored once per nonce, and a retry with the same nonce routes it again (the web replay marks the message's uploads used and hands its stored files over again). Routing: a question card waits = the text is the answer; an approval card waits = the message runs as a new run, the approval stays open; the scope has an active run = a steering row; else a new run. A new owner run cancels older owner runs of the scope that never started (their text is copied into steering first). A reply that is exactly one emoji of `REACTIONS` to a message of the conversation is a **reaction** (`run-intake-reaction.ts`), never a turn or steering: it wakes the bot that wrote the message with a `reaction` run (may end in `NO_RESPONSE`, no progress updates) only when only reactions came after that message, no run of the bot is busy in the conversation and the bot was not woken by a reaction within `limits.reactionCooldownMs` (30 s); a 👍 or 👎 on a message of a run parked on a question answers it "yes" or "no" instead; otherwise the reaction is context only. The web folds reactions under their message as chips and offers the six emoji from the React button (hover) or the hold sheet (phone).
- **Steering** (`steering` table, `run-steering.ts`): a message sent while the bot works is pushed into the live session between model steps. A row counts as answered only if it went with the first turn or a later tool result followed its push; otherwise it becomes a continuation run (also after a failed run, once). Held rows (non-conversational run) become a continuation when the run ends or parks.
- **Run life** (`run-executor.ts`, `run-session.ts`, `run-pump.ts`): claim, publish "working", open the stored SDK session (resume; memory, group context and effort are loaded fresh at every open), push the turn and steering, stay open until the turn and every background subagent ended (plus a 15 s follow-up grace), then finish in one fenced transition. A cut run resumes with a "your previous turn was cut" note; 3 cut attempts stop it as `interrupted` (a graceful stop is not a cut). A stream with no SDK event for 180 s and no tool running is aborted. A transient error requeues with backoff, up to 5 times; 8 setup failures in a row fail the run. Subagents of one bot run at most `limits.maxParallelSubagents` (4) at once (`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`, set by the app only). A worker runs up to 4 runs at once and claims nothing while available memory is below 512 MB (`workers/free-memory.ts`: macOS `vm_stat` free + inactive + speculative pages, Linux `MemAvailable`; read every 5 s at most; an unreadable value never blocks).
- **Cards** (`cards` table, `run-cards.ts`, `run-card-answer.ts`; web `card-desk.ts`): approval and question cards are rows; they never expire (one reminder after 4 h). A parked run ends its turn and frees the worker; while a background subagent still runs it stays open and parks after. An answer requeues the run; the resumed session is told to call exactly the approved input, and the gate allows that call once (hash of tool and input). Approval input is shown whole up to 20000 code points; a longer one offers only Deny.
- **Stop** (`run-stop.ts`): each active run of the scope or conversation is cancelled by its own fenced transition (retried when a worker claims it meanwhile), then its steering and cards are dropped; the reconciler repairs what a crash left between the steps; a cancel hint plus the once-a-second fence check abort the session.
- **Results** (`outcome-outbox.ts`, `outcome-reconciler.ts`): a finished run keeps its result on the row; the reconciler re-sends every 30 s until "returned at" is set; send keys make a re-send idempotent. The same sweep repairs steering rows bound to terminal or cancelled runs.
- **Effects** (`effect_calls` table, `effect-key.ts`): effect tools record each call by key (`<wakeId>:<cardId>:<tool>:<inputHash>:<n>`) before acting. A re-run after a cut gets the stored result, or a warning that the call may have run already.
- **Shared state in the db:** chain caps from `wakes`, spend, `SetEffort` level and the idle-flush time per scope (`scopes`), bot status from run rows. Memory files take a cross-process lock per owner.
- **Known limits:** a lost worker-to-main post is only seen after a web refetch; a resumed model may send the same tool input again; a background task that never reports holds the scope until Stop; many-machine workers need Postgres (later).

## Scheduled runs (engine, chat tools, API and web)

- **Run kind `schedule`:** background priority, starts untainted, the task text counts as the owner's words, same session as the target conversation; only `ScheduleList` is available among the schedule tools.
- **Chat tools** (`packages/tools/src/schedules`): `ScheduleCreate`, `ScheduleList`, `ScheduleUpdate`, `ScheduleDelete`. Every bot gets the `schedules` server (like scratchpad); `ScheduleCreate` and `ScheduleList` are `alwaysLoad`. A clean owner run needs no card; a tainted, bot or ticket run asks for Create, Update and Delete.
- **Permission in a scheduled run:** read steps (`WebFetch`, read-classified external MCP calls) are allowed even over an owner `require_approval` rule and the autonomy level. The sandbox floor and per-tool deny still apply. Writes still ask. Scheduled reads are not recorded as owner approvals for the taint logic (`scheduled-read.ts`, `taint-policy`).
- **API and contract:** `packages/contracts` has a `schedules` contract area and `ScheduleDto`, `ScheduleRunDto`, `RepeatRuleDto` (`dto/schedules.ts`); the router is `packages/api/src/routers/schedules`. `runNow` takes a `nonce`, so a double click is one run. `runs` pages 20 at a time, newest first (`before` is a `firedAt`).
- **SSE `schedule` event:** `{ type: "schedule", id }` is sent when a schedule or one of its runs changes, including a schedule a bot made in chat; the web app refetches that schedule and the list.
- **Message tag:** `messages.schedule_id` and `schedule_name` (migration 0015) are set when a scheduled run posts; `MessageDto.schedule` is `{ id, name }`. The columns outlive the schedule and its wake; `schedule_name` is unset when the schedule was already gone.
- **Web screens** (`apps/web/src/components/schedules`): `/schedules` list (phone: Settings, Schedules), `/schedules/:id` page with form, runs and delete, a New schedule sheet (`/schedules?new=1`), Run now (shows "Still running" while the previous run waits), and a schedule tag on a posted message that links to the schedule.
- **Retention:** history 90 days; a schedule disabled with `bot_gone` or `group_gone` is removed after 8 days. The Axiom allow-list adds `scheduleId`.
- **Residual risk:** with the open network (owner decision) a scheduled run can read a page or tool output and then send readable data out through a tool that is already allowed. Automatic reads do not make writes automatic, but a prompt-injection read-then-send path through an allowed write or network tool is known and not closed.
- **Known limits:** the notice-once-a-day map is in memory (a notice can repeat after a restart); a tiny race window between `runNow` and a tick.

## Computers (not verified live)
- **What:** a bot whose file names `computer: <name>` drives its own Linux computer (desktop and a Chromium that keeps its logins). The computer is made by a provider plugin from the `computer` block of `settings.yaml` (`provider: { id, ... }`, `slots`, `perBotCpus`, `perBotMemoryMb`, `cpus`, `memoryMb`). First plugin: Cua (`packages/computer-cua`).
- **Plugin:** `ComputerProviderPlugin` (core port: `id`, `parseOptions`, `check`, `create`); the app lists plugins in `apps/friday/src/computer-plugins.ts` (`COMPUTER_PLUGINS`). The plugin's options get the owner's `PATH` and `HOME` as `env` unless the entry sets its own; no other env reaches it.
- **Slots:** each process counts the machine's slots at start, in the background, from the provider's capacity (`computeSlots`: per active bot 1 CPU and 1536 MB by default, 0.5 CPU and 512 MB reserved; `computer.slots` may only lower the number) and logs `computer.slots` with a readable text. The first computer call waits for that count. A failed count (Docker not running) is 0 slots with the reason; it is counted again on a later computer call, at most once per 30 s, and a recovered count logs `computer.slots`. A slot is a `slot:<botId>` hold row (TTL 120 s); input to one computer is an exclusive `input:<computer>` hold with a fence.
- **Slot heartbeat** (`packages/tools/src/computer/slot-heartbeat.ts`): while a session holds its slot, it renews it every 40 s, so a pause between calls does not free the slot to another bot while the Chromium still runs. The heartbeat stops when a renew fails (the run-end release or a takeover), and after 10 min without a computer call; a parked or abandoned session then gives the slot back through the TTL.
- **Never fails startup:** an unknown provider id, bad options, a failed `check` or a capacity error (Docker not running) is logged as `computer.problem` or as 0 slots with the reason. The bot still gets its `computer` server, whose tools refuse with that text.
- **Session wiring** (`apps/friday/src/computer-sessions.ts`): a bot with `computer` gets the `computer` MCP server (no `tools` entry needed): desktop tools (`ComputerScreenshot`, `ComputerAct`, `ComputerShell`) and page tools over raw CDP (`BrowserNavigate`, `BrowserSnapshot`, `BrowserAct`). Holder = the run's wake id. Each bot's Chromium uses the profile `/home/cua/friday-profiles/<botId>` and a cdp port fixed by its id: `9300 + fnv1a32(botId) % 700` (`computer-ports.ts`), so adding or removing bots does not move a running Chromium. When two bots on one computer hash to one port, the later id (sorted) takes the next free port (wrapping to 9300) and `computer.port_shifted` names both bots. `ComputerAct` waits are capped at 10 000 ms each, under the 30 s input lease.
- **Permissions:** computer tools (`inComputer` in `tools.yaml`) are allowed after the floor and per-tool deny, before taint, rules and level; they still taint the run.
- **Prompt:** the `<computer>` facts block (`computerContextBlock`) names the computer, the tools and the slot line; it sits in the system prompt after the bot's memory.
- **Run end (per run):** every terminal path calls `computerRelease(botId, wakeId)` (`run-computer-release.ts`) after its status transition: done and failed (`finishRun`), cancelled by the owner's Stop or from another process (`cutShort`), interrupted after too many restarts (`countCut`), dropped (`dropRun`); a graceful shutdown releases before the run is requeued. It acts only when this wake holds the bot's `slot:<botId>` row: then the browser closes gracefully (`Browser.close`, never a kill first) and that row is released. Another run of the same bot (direct, group or ticket) keeps its slot and its browser. A lost transition or a plain lost lease releases nothing (another worker runs the wake under the same holder). A release error is logged (`computer.release_failed`); the slot's TTL (120 s) frees it anyway.
- **Parked runs:** a run parked on a card is not ended and keeps its slot until the heartbeat stops and the TTL runs out; when it resumes, the same wake id is the holder again.
- **Run-end release and lapsed slots:** the release matches the run's `slot:<botId>` row even when its TTL has lapsed (any row not released), so the browser still closes.
- **Known limits:** input is sent through cua's `do` selection; until the live check proves that selection is per call, run computer bots with one engine process (`limits.workers: 0`) or one computer.
- **Bot files:** `computer` is set by the owner in the bot file. A `BotDesign` overwrite and a web edit keep it; the API returns it read only (`BotDto.computer`). Changing it restarts the bot's session.
